# Instructions for AI contributors

## Start here

This repository is a Scrum project management application with two independently built applications:

- `scrum-app-ui/`: Angular 20 frontend. Read its `AGENTS.md` before editing it.
- `scrum-app-api/`: Spring Boot 3.5.6 backend with Java 24 and PostgreSQL. Read its `AGENTS.md` before editing it.

Read `README.md`, then `docs/project-specification.md`, `docs/architecture.md`, and `docs/known-gaps.md` for context. For API work, also read `docs/api.md`. Source code takes precedence when documentation has drifted; update the documentation alongside a changed contract or workflow.

## Scope and repository boundaries

- Work from the root Git repository. Both application folders are tracked source directories, not submodules; do not initialize nested Git repositories.
- Keep the frontend and backend folder names and their separate npm/Gradle builds unless the user requests a restructuring.
- Preserve unrelated working changes. Check `git status` before editing.
- Treat `docs/design/legacy/`, `scrum-app-ui/mockups/`, and `docs/history/` as design/history references. Their features, dates, and testing claims are not evidence of current behavior.
- `.local-backups/` contains private pre-import configuration, scripts, and frontend Git metadata on the original machine. It is ignored, is not part of a clone, and must not be staged or uploaded.

## Domain rules to preserve

- Every project belongs to one user. Project management access must be checked against that owner on the backend.
- Every authenticated user can be a project manager. An assignee role comes from a `user_assignees` link, not a global role field on the user.
- Assignee identity is separate from user identity. A user may link multiple assignee records; each assignee can link to only one user.
- Sprint access for an assignee comes from tasks assigned to linked assignees. Assignee API queries must filter by the current user, sprint, and assignment.
- Project browser routes use `projectCode`; backend resource paths use project UUIDs. Resolve the code before making scoped calls.
- Tasks always belong to a sprint and project. Assignee, department, and dependency are optional; referenced records must stay within the project.
- Status values are `TODO`, `IN_PROGRESS`, `DONE`, `CLOSED`; priorities are `HIGH`, `MEDIUM`, `LOW`.
- The assignee UI offers only `TODO`, `IN_PROGRESS`, and `DONE` and hides closed tasks. The backend currently accepts `CLOSED`; this is a documented gap, not permission to weaken the intended restriction.
- Task codes and master-data codes are generated by backend counters. Dependencies must not form cycles; a task with dependents cannot be deleted through the task service.
- One assignee can have several department memberships, with at most one marked as priority across all departments.
- Scheduling and capacity calculations currently differ. Read `docs/known-gaps.md` before changing dates, story point conversion, holidays, or capacity.

## Changes across applications

- Preserve the API envelope (`success`, `message`, `data`, `error`) and backend error codes. Backend JSON omits null properties; callers must tolerate omitted `data`/`error`.
- Coordinate Java DTO/entity changes with TypeScript interfaces, HTTP services, consuming components, and the API reference.
- A frontend guard is a navigation aid. Enforce ownership and assignment on the backend as well.
- Dates are `YYYY-MM-DD` for sprint/timeline fields. UUIDs are strings in TypeScript. JSON audit timestamps are strings even where older interfaces declare `Date`.
- Add schema changes as new versioned Flyway migrations. Preserve the checked-in V1–V14 migrations to avoid changing checksums on existing databases.
- Use PostgreSQL for database integration work: the implementation depends on native SQL, JSONB, partial indexes, and PostgreSQL functions.

## Local configuration and secrets

- Follow `docs/development.md`. Load the ignored root `.env` before running the backend; Spring Boot does not read it automatically.
- Required configuration includes `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`, and `PROJECT_KEY_MASTER_KEY`. Do not add credential defaults to committed YAML.
- Keep cryptographic keys stable for an existing database. Changing the project master key breaks decryption and deterministic project key lookups unless data is migrated.
- Never commit `.env`, tokens, private keys, logs, database exports, dependencies, build output, or local backups. Add safe variable names to `.env.example` when introducing configuration.
- Use disposable data for `scripts/manual-api/`. Some scripts create accounts or update a task; read their README and source before invoking them.

## Commands and reporting

- Run npm commands in `scrum-app-ui/` and `./gradlew` commands in `scrum-app-api/`; there is no root build command.
- Frontend: `npm ci`, `npm start`, `npm run build`, `npm test -- --watch=false`.
- Backend: `./gradlew bootRun`, `./gradlew bootJar`, `./gradlew test` with the environment and database configured.
- Choose checks appropriate to the user's request. Do not run scripts that create accounts or alter tasks as routine documentation checks.
- The repository has no configured end-to-end suite or CI. Existing tests provide limited evidence, and the H2 profile is unverified for native queries.
- Explain what changed, what was actually checked, and any remaining uncertainty. Never repeat historical test claims as fresh verification.
